# Part 3. 프레젠테이션 레이아웃

지금까지(Part 1·2)가 **"무엇을 쓸 것인가"** 였다면, 이 파트는 **"어떻게 보여줄 것인가"** 입니다.
같은 내용이라도 배치에 따라 전달력이 완전히 달라집니다.

> 특히 여러분의 기술 문서에는 **다이어그램(FSM·클래스·시퀀스)** 이 들어갑니다.
> 이 정보를 읽는 사람에게 잘 전달하려면, 다이어그램을 **어떤 화면에 어떻게 배치하느냐**가 중요합니다.
> 이 파트는 그 레이아웃의 종류·원칙·스타일을 다룹니다.

## 3-1. 레이아웃이 정보 전달을 좌우하는 이유

사람은 슬라이드/페이지를 **읽지 않고 먼저 봅니다.** 시선은 보통
왼쪽 위 → 오른쪽 아래(Z자)로 흐릅니다. 좋은 레이아웃은 이 흐름에 맞춰
**"가장 중요한 것"을 시선이 처음 닿는 곳에** 둡니다.

레이아웃 설계의 3원칙:

- **한 화면 한 메시지** — 슬라이드 하나에 주제 하나. 두 개면 두 장으로 나눕니다.
- **정렬과 여백** — 요소를 격자에 맞춰 정렬하고, 여백을 두려워하지 마세요.
  빽빽함은 "정리 안 됨"으로 읽힙니다.
- **위계(Hierarchy)** — 제목 > 소제목 > 본문 > 캡션. 크기·굵기·색으로 위계를 만듭니다.

> **와이어프레임 표기 안내**: 아래 레이아웃들은 화면 구조를 박스 그림으로 표현합니다.
> 이 표기는 GitHub와 Marp 슬라이드 양쪽에서 그대로 렌더링됩니다.

## 3-2. 레이아웃 유형 카탈로그

기술 문서/포트폴리오에서 반복적으로 쓰이는 **8가지 핵심 레이아웃**입니다.
각 유형마다 *용도 · 구조 · 나쁜 예*를 함께 봅니다.

### ① 표지 (Title / Cover)

문서의 첫인상. 이름·프로젝트명·연락처·한 줄 정체성을 담습니다.

```
┌─────────────────────────────────┐
│                                 │
│         CraftingSystem          │  ← 프로젝트명 (가장 큼)
│      Technical Documentation    │  ← 부제
│                                 │
│                                 │
│   김재훈 (Jay)                    │  ← 작성자
│   jay.dev@email.com · GitHub    │  ← 연락처
└─────────────────────────────────┘
```

- **용도**: 기술 문서·포트폴리오의 첫 장. (샘플 `CoreMerge`가 이 형식)
- **원칙**: 요소를 최소화하고 가운데 정렬. 프로젝트명이 압도적으로 커야 합니다.
- **나쁜 예**: 표지에 목차·기술 스택까지 우겨넣기 → 첫인상이 산만해집니다.

### ② 목차 (Agenda / Contents)

읽는 사람에게 **전체 지도**를 줍니다. 긴 문서일수록 필수입니다.

```
┌─────────────────────────────────┐
│  CONTENTS                       │
│                                 │
│  1  개요          5  결과·회고     │  ← 2열로 나눠 균형
│  2  시스템 구조                    │
│  3  핵심 기능                      │
│  4  고민과 선택                    │
└─────────────────────────────────┘
```

- **용도**: 표지 다음 장. 5단 구조를 그대로 목차로.
- **원칙**: 번호 + 짧은 제목. 항목이 많으면 2열로 균형을 맞춥니다.
- **나쁜 예**: 목차에 설명 문장까지 붙이기 → 목차는 '이정표'지 '본문'이 아닙니다.

### ③ 개요 / 요약 (Overview)

What과 Why를 한 화면에. 좌측에 텍스트, 우측에 대표 이미지·마일스톤을 배치하면 균형이 좋습니다.

```
┌─────────────────────────────────┐
│  개요                            │
│ ┌──────────────┐ ┌────────────┐ │
│ │ What         │ │            │ │
│ │  재료 소비 제작 │ │  스크린샷    │ │
│ │ Why          │ │  또는       │ │
│ │  UI/로직 분리  │ │  마일스톤    │ │
│ │ 환경·기간·링크  │ │            │ │
│ └──────────────┘ └────────────┘ │
└─────────────────────────────────┘
```

- **용도**: 기술 문서 개요 섹션. (원본 가이드의 "1장 or 2장" 개요)
- **원칙**: 좌 텍스트 / 우 비주얼의 6:4 분할. 텍스트는 불릿 3~5개로 압축.
- **나쁜 예**: 개요에 코드를 넣기 → 개요는 '결론 요약'이지 '구현'이 아닙니다.

### ④ 다이어그램 중심 (Diagram-Centric) ★

**이 가이드의 핵심 레이아웃.** FSM·클래스·시퀀스 다이어그램이 주인공인 화면입니다.

```
┌─────────────────────────────────┐
│  시스템 구조 — 클래스 관계          │  ← 제목은 짧게
│                                 │
│   ┌────────────────────────┐    │
│   │                        │    │
│   │   [다이어그램 크게]       │    │  ← 화면의 70% 이상
│   │                        │    │
│   └────────────────────────┘    │
│   ▸ Manager가 인터페이스에 의존    │  ← 한 줄 캡션(핵심만)
└─────────────────────────────────┘
```

- **용도**: Part 4의 Mermaid 다이어그램을 보여주는 모든 화면.
- **원칙**: **다이어그램이 화면의 주인공.** 설명은 다이어그램 안(라벨)에 넣고,
  바깥 텍스트는 "이 그림에서 봐야 할 핵심" 한 줄로 제한합니다.
- **나쁜 예**: 다이어그램을 구석에 작게 넣고 옆에 설명을 잔뜩 → 그림을 볼 이유가 사라집니다.

> **왜 별표(★)인가**: 여러분의 FSM·클래스·시퀀스 다이어그램은 이 레이아웃에서 가장 잘 삽니다.
> 다이어그램은 '크게, 하나씩, 캡션 한 줄'이 원칙입니다.

### ⑤ 코드 + 설명 2단 (Code & Explanation)

핵심 기능 섹션의 단골. 코드와 "왜 이렇게 짰는지"를 나란히 놓습니다.

```
┌─────────────────────────────────┐
│  핵심 기능 — RequestCraft         │
│ ┌──────────────┐ ┌────────────┐ │
│ │ // 검증 먼저   │ │ ▸ 소비 전    │ │
│ │ if(!Has...)   │ │   검증으로   │ │
│ │   return;     │ │   재료 유실  │ │
│ │ var s = roll..│ │   방지       │ │
│ │ Consume(...)  │ │ ▸ roll 주입  │ │
│ └──────────────┘ └────────────┘ │
│   좌: 코드 스니펫     우: 설명       │
└─────────────────────────────────┘
```

- **용도**: 핵심 기능/사용법 섹션.
- **원칙**: 좌측 코드는 **50줄 이하 핵심만**, 우측은 "왜"를 불릿으로. 좌우 행을 맞춥니다.
- **나쁜 예**: 500줄 코드를 통째로 → 원본 가이드가 말한 "최악의 설명서".

### ⑥ 비교 (Comparison / Trade-off) ★

**고민과 선택 섹션의 핵심.** 대안 A와 B를 좌우로 대칭 배치해 판단 근거를 보여줍니다.

```
┌─────────────────────────────────┐
│  고민과 선택 — 결과 전파 방식        │
│ ┌──────────────┐ ┌────────────┐ │
│ │ [A] 직접 참조  │ │ [B] 이벤트   │ │
│ │ + 직관적       │ │ + 느슨한 결합 │ │
│ │ + 추적 쉬움    │ │ + 확장 용이  │ │
│ │ − 강한 결합    │ │ − 흐름 추적↓ │ │
│ └──────────────┘ └────────────┘ │
│   ▸ 결정: B (확장 대상이 늘어남)     │  ← 결론 강조
└─────────────────────────────────┘
```

- **용도**: Trade-off 설명. Pros/Cons를 대칭으로.
- **원칙**: 좌우 항목 수를 맞추고, **하단에 최종 결정과 이유**를 강조 배치.
- **나쁜 예**: 한쪽만 길게 → 비교가 아니라 '결론 정해두고 끼워맞추기'로 보입니다.

### ⑦ 타임라인 / 프로세스 (Timeline / Flow)

개발 과정, 처리 순서, 마일스톤을 시간·단계 순으로.

```
┌─────────────────────────────────┐
│  처리 흐름                        │
│                                 │
│  요청 ──▶ 검증 ──▶ 판정 ──▶ 결과    │  ← 가로 흐름
│   06월      07월      08월          │
└─────────────────────────────────┘
```

- **용도**: 시퀀스·플로우차트 요약, 개발 마일스톤.
- **원칙**: 왼→오른쪽 단방향. 단계는 3~5개로 제한.
- **나쁜 예**: 화살표가 사방으로 얽힘 → 순서가 안 읽힙니다. (복잡하면 Mermaid로)

### ⑧ 회고 / 마무리 (Summary / Closing)

결과·배운 점·향후 계획을 정리하는 마지막 장.

```
┌─────────────────────────────────┐
│  결과 및 배운 점                   │
│  ✓ 달성   UI/로직 분리, 테스트 100% │
│  △ 아쉬움  Recipe 하드코딩          │
│  → 계획    ScriptableObject 전환   │
└─────────────────────────────────┘
```

- **용도**: 문서의 마지막 섹션. (샘플들이 "회고"로 마무리)
- **원칙**: 달성/아쉬움/계획을 기호(✓ △ →)로 시각 구분.
- **나쁜 예**: "열심히 했습니다"류의 감상 → 데이터와 다음 계획이 없으면 공허합니다.

### 유형 요약

| 레이아웃 | 주 용도 | 기술 문서 섹션 |
|---|---|---|
| ① 표지 | 첫인상 | 문서 시작 |
| ② 목차 | 전체 지도 | 표지 다음 |
| ③ 개요 | What/Why 요약 | 1. 개요 |
| ④ 다이어그램 중심 ★ | 구조 시각화 | 2. 시스템 구조 |
| ⑤ 코드+설명 2단 | 구현 증명 | 3. 핵심 기능 |
| ⑥ 비교 ★ | 판단 근거 | 4. 고민과 선택 |
| ⑦ 타임라인/프로세스 | 순서·흐름 | 2·3. 구조/기능 |
| ⑧ 회고 | 정리·전망 | 5. 결과 및 배운 점 |

> ★ 표시(④·⑥)는 **여러분의 다이어그램이 가장 잘 사는** 레이아웃입니다.
> Part 6에서 이 레이아웃들을 AI로 생성하는 프롬프트를 제공합니다.

## 3-3. 스타일 · 테마 방향

레이아웃이 '뼈대'라면, 스타일·테마는 '피부'입니다. 개발자 문서에 어울리는 3가지 방향입니다.

### 미니멀 / 문서형 (권장 기본값)

- **느낌**: 흰 배경, 검은 글씨, 포인트 컬러 1개. 논문·기술 블로그 톤.
- **어울림**: 대부분의 기술 문서. 내용에 집중시키고 싶을 때.
- **폰트**: 본문은 가독성 높은 산세리프(예: Pretendard, Noto Sans),
  코드는 고정폭(예: JetBrains Mono, D2Coding).
- **컬러**: 배경 흰색 + 텍스트 진회색(#222) + 강조 1색(파랑/청록 계열).

### 다크 코드 테마

- **느낌**: 어두운 배경에 밝은 코드. IDE(예: Rider의 다크 테마) 감성.
- **어울림**: 코드 스니펫이 많은 문서. 개발자 대상 발표.
- **주의**: PDF 인쇄 시 잉크 소모·가독성 문제. **발표용/화면용에 적합**, 제출용은 밝은 테마 권장.

### 브랜드 / 프로젝트 테마

- **느낌**: 프로젝트의 세계관 색을 입힘. (예: 생존 게임이면 흙·나무 톤)
- **어울림**: 포트폴리오 요약 문서, 게임 프로젝트.
- **주의**: 분위기가 가독성을 해치지 않는 선에서. **정보 > 분위기**.

### 테마 선택 기준

| 상황 | 권장 테마 |
|---|---|
| 기업 제출용 PDF | 미니멀 / 문서형 (밝은 배경) |
| 개발자 대상 발표 | 다크 코드 테마 |
| 포트폴리오 첫인상 | 브랜드 테마 (단, 본문은 미니멀 유지) |

> **일관성이 핵심입니다.** 폰트 2종(본문·코드), 컬러 3색(배경·텍스트·강조) 안에서
> 문서 전체를 통일하세요. 장마다 스타일이 바뀌면 "정리 안 됨"으로 읽힙니다.

## Part 3 정리

- 레이아웃은 **한 화면 한 메시지 · 정렬과 여백 · 위계** 3원칙 위에 세웁니다.
- 8가지 유형 중 **④ 다이어그램 중심**과 **⑥ 비교**가 여러분의 다이어그램·판단 근거를
  가장 잘 전달합니다.
- 테마는 **미니멀(제출) / 다크(발표) / 브랜드(포트폴리오)** 중 목적에 맞게, 단 **일관성** 유지.
- 다음 파트(Part 4)에서는 이 레이아웃에 들어갈 **다이어그램을 Mermaid로 그리는 법**을 다룹니다.
